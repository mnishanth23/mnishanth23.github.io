Moving from Jenkins to Drone CI: what changed, and what I’d do again

18 Aug 20267 min read

By Nishanth M · DevOps Engineer | SRE

Moving our CI/CD from Jenkins to Drone CI was supposed to be a tooling change. It turned into a lesson about what actually makes deployments boring: not the CI server, but the gates you put around every release.

This is a write-up of what changed, what surprised me, and what I’d repeat. It’s from the point of view of someone who runs the pipelines day to day, not someone who evaluated CI products for a living.

Why move at all

The goal was maintainability and release reliability. Jenkins can do almost anything, and that’s the problem: over time, a lot of behaviour ends up in places that are hard to review. Some of it lives in a Jenkinsfile, some in job configuration in the UI, and some in plugins that each have their own upgrade cycle.[5]

Drone takes the opposite approach. A pipeline is a YAML file in the repository, and every step runs in its own container.[1] There is much less you can do outside the pipeline file, which turned out to be a feature.

Pipeline-as-code, for real

“Pipeline-as-code” exists in Jenkins too, but in Drone it’s the only way. That changes how a team works with pipelines:

  • Changes are reviewed like code. A new step, a changed condition or a removed gate shows up in a diff.
  • The pipeline travels with the branch. If a branch needs a different build, the change is in that branch, not in a shared job.
  • Steps are containers. The tools a step needs are in its image, so “works on the agent” problems mostly go away.[2]

Here’s the shape of a pipeline, heavily simplified:

Kaniko → Harbor → Trivy

The build-and-ship path is the same for every service, which is most of its value:

  1. Kaniko builds the image from the Dockerfile inside a container, without a privileged Docker daemon on the runner.
  2. Harbor stores it, tagged so that any running version traces back to a commit.
  3. Trivy scans the image. For stage, the scan is blocking: if it fails, nothing moves forward.

The important word is blocking. A scan that only produces a report is a scan nobody reads. A scan that fails the build gets fixed, or gets an explicit, reviewed exception.

Secrets and the jump host

In Drone, credentials are stored as secrets and pulled into a step with from_secret, instead of being pasted into job configuration.[3] That makes it obvious which step can see which credential, which is exactly the question you want to answer quickly during a review.

Deployment goes over SSH through a jump host. Target servers aren’t reachable from CI directly; the deploy step connects through the bastion and pulls the exact tagged image from Harbor. What was scanned is what runs.

Migrating without a big bang

The approach I’d recommend, and the one I’d use again, is to migrate one pipeline at a time and keep the old path available until the new one has proven itself:

  • Start with a service that deploys often, so the new pipeline gets exercised quickly.
  • Run the new pipeline alongside the old one for a while and compare what each produces.
  • Only switch the deploy over once the build, scan and deploy steps behave the same way.
  • Retire the old job deliberately, not by forgetting about it.
Lesson

Don’t port pipelines line by line. A migration is the cheapest moment you’ll ever get to delete steps nobody can explain.

Rollback is a tag

Because every release is an image tag in Harbor, rolling back means deploying the previous tag: no rebuild, no guessing which commit was live. It’s the single change that made releases feel less risky.

The review that mattered more

Moving to Drone made the pipelines readable. Reading them is what found the real problems. When I reviewed the backend service pipelines (brain and portal-service among them), the same gaps kept showing up, and closing them is what got us to minimum-failure production deployments:

  • Post-deploy health checks. A deploy isn’t successful when the container starts; it’s successful when the service answers.
  • Blocking scans for stage. Trivy findings stop the pipeline instead of becoming a log line.
  • Concurrency limits. Two runs never deploy over each other.
  • Manual gates before stage. Someone looks at the change before it reaches a shared environment.
  • Failure notifications. A red pipeline that nobody hears about is worse than no pipeline.
None of these are clever. All of them are boring. That’s the point.

They line up with what the research on delivery performance keeps finding: small, frequent, well-tested changes with fast recovery beat big, careful, infrequent ones.[6][7] Keeping stage close to production matters for the same reason: a gate only means something if the environment behind it behaves like the one you’re protecting.[8]

What I’d do again

  1. Put the whole pipeline in the repo. If it isn’t in the diff, it isn’t reviewed.
  2. Make every gate blocking or remove it. Advisory gates train people to ignore gates.
  3. Release by tag, so rollback is a deploy, not a rebuild. (Next step: make tags immutable and deploy by digest.)
  4. Review pipelines after migrating, service by service. The migration is where you get readable pipelines; the review is where you get reliable releases.

Next on my list is deploying by image digest, signing images in CI, and wiring the health check straight into an automatic rollback. If you’ve done any of those on Drone, I’d like to hear how it went.[4][9]
