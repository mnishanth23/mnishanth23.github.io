Elasticsearch 7.11.2 → 7.17.28: the required stop before 8.x

6 Oct 20266 min read

By Nishanth M · DevOps Engineer | SRE

You can’t go straight from an early 7.x Elasticsearch to 8.x. There’s a required stop on the way, and that stop is 7.17. I took our dev Elasticsearch and Kibana from 7.11.2 to 7.17.28. This post covers why that step exists, how it works, and what still has to happen before 8.x.

To be clear about where things stand: the dev stack now runs 7.17.28. The 8.x upgrade is planned and hasn’t been done yet. Most of this post is about making sure that next step is boring.

Why you can’t skip 7.17

Elastic’s upgrade guide is explicit: to upgrade to 8.x from 7.16 or earlier, you must first upgrade to 7.17. That holds even if you plan a full-cluster restart rather than a rolling upgrade.[1] The only way around it is to stand up a fresh 8.x cluster and reindex from remote.

The reason is tooling, not just version numbers. 7.17 is the last 7.x minor, and it’s the release that knows what 8.x will reject. Its Upgrade Assistant and deprecation checks are written against 8.x, so they can tell you what will break before you find out the hard way.[4]

Getting to 7.17 from 7.11 is the easy part. A rolling upgrade from any 7.0–7.16 release straight to 7.17 is a supported path, with no intermediate minors required.[2]

What I upgraded, and why dev first

The scope was our dev Elasticsearch and Kibana, both from 7.11.2 to 7.17.28. Starting in dev was deliberate. I work across devlab, stage, UAT and E2E environments, and dev is where an upgrade can go wrong cheaply. Every surprise found there is one that won’t surprise anyone on a shared environment.

Snapshot first: there is no downgrade

Elasticsearch doesn’t support in-place downgrades. Once a cluster contains nodes on the new version, its internal state can change in ways that can’t be reverted. If an upgrade fails partway, the documented way back is a fresh cluster on the old version, restored from a snapshot.[2][3][11] So the snapshot comes before anything else:

The Kibana part matters as well. Kibana migrates its saved objects automatically when a new version starts, and rolling Kibana back needs a snapshot that includes its .kibana* indices.[6] A snapshot you’ve never restored is a hope, not a backup, so restoring it into a scratch cluster at least once is worth the time.

Rolling upgrade or full-cluster restart

There are two ways to swap the binaries:

  • Rolling upgrade: one node at a time, so the cluster stays available. You stop replica allocation so the cluster doesn’t rush to re-replicate a node that’s coming straight back, upgrade and restart the node, re-enable allocation, and wait for green before moving to the next one.[3]
  • Full-cluster restart: stop every node, upgrade them all, start them again.[12] It causes downtime, but it’s simpler, and on a single-node dev cluster it’s effectively the only option anyway.

Kibana goes second, on the same version

Elasticsearch is upgraded first, then Kibana, and the two should end up on the same version. Kibana on an older version than Elasticsearch works temporarily, with a warning at startup, precisely to make that order possible. Running different versions isn’t a configuration to stay on.[7]

Two rules from the Kibana upgrade guide are easy to miss. First, shut down all Kibana instances before upgrading, because several Kibana versions running against the same indices is unsupported and can lose data. Second, give the saved-object migration time to finish on first start, and check its logs before calling the upgrade done.[6]

“Done” deserves an end-to-end check, not just a green process list:

  • Every node reports the new version, and cluster health is back to green.
  • Kibana’s status page is healthy, and existing dashboards, saved searches and index patterns still open.
  • Whatever writes to the cluster is still writing: fresh documents are arriving in the indices you expect.
  • The deprecation log is worth reading straight away. 7.17 knows about more of 8.x than 7.11 did, so new warnings after the upgrade are expected, and they’re your first look at the 8.x to-do list.
Where things stand

Dev Elasticsearch and Kibana: upgraded from 7.11.2 to 7.17.28, on matching versions. 8.x is next, and it hasn’t been done yet.

What 7.17 unlocks for 8.x

Being on 7.17 is what makes the 8.x upgrade something you can plan:

  • The Upgrade Assistant (Kibana › Stack Management) lists deprecated settings and features, and walks you through fixing them. That includes reindexing any indices created before 7.0, which 8.x can’t read. Every critical issue has to be resolved before upgrading.[1][4]
  • Deprecation logs show what your clients are doing, not just your configuration. CRITICAL entries mark features that will be removed in the next major version. Deprecation logs can also be indexed into a data stream, which makes them searchable from Kibana, and setting an X-Opaque-Id header lets you trace each one back to its caller.[5]
  • The deprecation info API is what the assistant uses underneath, if you’d rather script the checks.[8]
  • Compatibility bridges. Beats and Logstash 7.17 work with Elasticsearch 8.x, so the clients don’t all have to move in the same window. 8.x also offers a REST API compatibility mode for 7.x-style requests, but that’s meant as a bridge, not a destination.[1]

What still has to happen before 8.x

This is the list I’m working from. None of it is done yet, and none of it should be rushed:

  1. Clear the Upgrade Assistant to zero critical issues.
  2. Let deprecation logs collect real traffic for a while, so occasional jobs and rarely used clients show up too.
  3. Read the 8.0 breaking changes, and those of every 8.x minor up to the target release.[9] Some are quiet behaviour changes. For example, action.destructive_requires_name now defaults to true, so wildcard deletes stop working. Others are removed settings that stop a node from starting at all.
  4. Check plugin and client compatibility against the target version.[10]
  5. Take a fresh snapshot and run the 8.x upgrade in dev first, the same way as this one.

What I’d tell myself before starting

  • Treat 7.17 as a milestone of its own, not a stepping stone you rush through. Most of the 8.x preparation happens here.
  • Snapshot, then restore-test the snapshot. No in-place downgrade means the snapshot is the rollback plan.
  • Upgrade Elasticsearch first, then Kibana, and end up on matching versions.
  • Start in dev. It’s the cheapest place to learn what the next environment will need.

Once the 8.x upgrade has actually happened, I’ll write it up properly, including whatever the Upgrade Assistant turns up along the way.
