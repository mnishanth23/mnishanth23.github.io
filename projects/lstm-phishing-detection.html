From e-mail to verdict

01

Overview

Phishing e-mails are written to look ordinary, so a filter that only checks for known bad words or links misses a lot. This project builds a system that detects phishing e-mails using Long Short-Term Memory (LSTM) networks, a type of recurrent neural network (RNN) known for its effectiveness in sequential data analysis.

An e-mail is a sequence: the order of the words carries meaning. An LSTM reads the message token by token and keeps a memory of what came before, so it can pick up phrasing patterns rather than isolated keywords.

The aim was a model that works on big e-mail data, so the preprocessing had to scale with the corpus, not just with a sample. The findings were presented at ICRTSET 2K23, an international conference.

02

Approach

  1. Prepare the text. Raw e-mails are cleaned and normalised, then tokenised and padded into fixed-length sequences so every message has the same shape going into the network.
  2. Embed. An embedding layer turns each token into a dense vector, so words used in similar ways end up close together.
  3. Read the sequence. The LSTM layer processes the vectors in order and carries context across the message.
  4. Classify. A final classifier layer scores the sequence and labels the e-mail phishing or legitimate.
  5. Wrap it in a web app. A small Flask front end lets a user sign up, log in, work with the training data and check messages through the browser.

03

What I learned, and what I’d do differently today

The main lesson: the model is the small part. Getting messy e-mail text into a consistent shape is what decides how far the model can scale.

Looking at it now as a DevOps engineer, this is what I’d change to make it something you could run and hand over:

  • Containerise it. One image with pinned Python and library versions, so the environment that trained the model is the one that serves it.
  • Serve it properly. Run the Flask app under a production WSGI server instead of the development server, with a /health endpoint a deploy can check.
  • Version the model like an image. Store each trained model as a tagged artefact, so a bad model is rolled back by re-deploying the previous tag, the same way I roll back services at work.
  • Put it through CI. Tests for the preprocessing step, an image scan before anything ships, and a build that fails loudly instead of a notebook that “worked on my machine”.
  • Keep secrets out of the code. Database and mail credentials come from environment variables or a secret store, never from the repository.
  • Watch it in production. Request latency, error rate and the share of e-mails flagged over time, so drift shows up on a dashboard before users notice.
