Drone CI pipeline hardening

I migrated our CI/CD from Jenkins to Drone CI and now maintain the Drone pipelines that build, scan and ship our services: images built with Kaniko, pushed to Harbor, scanned with Trivy, and deployed over SSH through a jump host with tag-based rollback. A review of the backend service pipelines then closed the gaps that let problems slip through. The result is consistently reliable, minimal-failure production deployments.

How a release flows

01

The problem

Our CI/CD ran on Jenkins. The aim of moving was simple: pipelines that are easier to maintain and releases that are more reliable.

Migrating the tool only solved half of it. When I later reviewed the backend service pipelines (brain and portal-service among them), the same kinds of gaps kept showing up — the sort that let a bad release look fine until someone noticed:

  • No post-deploy health check, so a deploy could “succeed” with the service down.
  • Image scans that didn’t block promotion to stage.
  • No concurrency limits, so two runs could deploy over each other.
  • No manual gate before stage.
  • Failures that nobody was notified about.

02

What I did

  1. Migrated CI/CD from Jenkins to Drone CI, moving pipelines into YAML that lives next to the code.
  2. Standardised the build-and-ship path: Kaniko builds the image, Harbor stores it, Trivy scans it, and deploys go over SSH through a jump host.
  3. Made rollback a tag change: every release is an image tag in Harbor, so rolling back means re-deploying the previous tag instead of rebuilding.
  4. Reviewed the backend service pipelines and closed the gaps: post-deploy health checks, blocking scans for stage, concurrency limits, manual gates before stage and failure notifications.

03

How it works

Build: Kaniko, no Docker daemon

Kaniko builds container images from a Dockerfile inside a container, without needing a privileged Docker daemon on the runner. The image is pushed to Harbor with a tag tied to the build, so any deployed version can be traced back to the commit that produced it.

Scan: Trivy as a gate, not a report

Trivy scans the pushed image. For stage, the scan is blocking: if it fails, the pipeline stops and nothing moves forward. A scan that only writes a report is easy to ignore; a scan that fails the build gets fixed.

Gate: a person says “yes” before stage

A manual approval sits before stage. It’s a deliberate speed bump: the build, scan and checks are automated, but someone looks at what’s about to change before it reaches a shared environment.

Deploy: SSH through a jump host

Target hosts aren’t reachable directly from CI. Deploy steps connect through a jump host (bastion) and pull the exact tagged image from Harbor, so what was scanned is what runs.

Verify: health check after every deploy

A deploy isn’t done when the container starts; it’s done when the service answers. The post-deploy health check makes the pipeline fail when the new version isn’t healthy, which also triggers the failure notification.

Rollback

Because every release is a tagged image in Harbor, rollback is just a deploy of the previous tag: no rebuild, no guessing which commit was live.

04

Results

  • Consistently reliable, minimal-failure production deployments after closing the pipeline review gaps.
  • Easier pipelines to maintain: pipeline-as-code in Drone instead of Jenkins jobs.
  • Rollback without a rebuild: re-deploy the previous image tag from Harbor.

05

What I’d do next

  • Deploy by image digest as well as tag, so a re-pushed tag can never change what runs.
  • Sign images in CI and verify the signature before deploy.
  • Wire the post-deploy health check to an automatic rollback to the previous tag.
  • Track deployment frequency, change failure rate and time to restore, so “minimal-failure” is a number on a dashboard.
