01

The problem

The document-processing platform needs two kinds of model at once: OCR models that turn page images into text, and an LLM that works with that text. All three models run on one NVIDIA A100 80GB, and they all want the same thing: GPU memory.

  • Models have to be served reliably, as long-running containers the platform can call, not as scripts someone starts by hand.
  • Several models share one GPU, so each one’s memory footprint and settings affect the others.
  • Without GPU metrics, a slow pipeline is guesswork: is the GPU saturated, is memory full, or is the bottleneck somewhere else?

02

What I did

  1. Deployed three vLLM model-serving containers on a single NVIDIA A100 80GB GPU server for the IDP platform, and I operate them.
  2. Deployed and tuned the Docker-based LLM/OCR inference containers: LightOnOCR-2, Chandra OCR 2 and a quantised Llama 3.1 8B, sharing the one GPU.
  3. Set up monitoring with the DCGM exporter (GPU), cAdvisor (containers) and node-exporter (host), scraped by Prometheus and shown in Grafana.

03

How it works

vLLM as the serving layer

vLLM serves a model behind an HTTP API, so the platform calls it like any other service. It’s built for throughput on GPUs: it batches incoming requests continuously and manages the attention cache in pages, so memory isn’t wasted on padding. Each of the three models runs as its own vLLM container with a pinned image and explicit settings, which makes a deploy repeatable and a rollback a matter of running the previous container.

Sharing one A100 80GB

vLLM reserves a set fraction of GPU memory up front for weights and its cache. With three vLLM containers on one GPU, that fraction is the main tuning lever: too high and the other containers can’t load, too low and the LLM handles fewer requests at once. The same thinking applies to context length: a longer maximum means a bigger cache per request.

Why a quantised Llama 3.1 8B

Quantization stores model weights at lower precision. The model takes less GPU memory, which leaves more room for the cache and for the OCR models next to it. The trade-off is some accuracy, so the choice is checked against the platform’s real documents rather than assumed.

Monitoring: DCGM exporter, cAdvisor and node-exporter → Prometheus → Grafana

NVIDIA’s DCGM exporter reads the GPU’s own counters (utilisation, memory in use, temperature, power) and exposes them as Prometheus metrics. cAdvisor adds per-container CPU and memory, and node-exporter covers the host itself. Prometheus scrapes and stores all three, and Grafana turns them into dashboards. Looking at GPU utilisation next to memory in use answers the first question in any slowdown: is the GPU the bottleneck or not?

What I’d do next

  • Alert on GPU memory and sustained utilisation, so saturation is caught before users notice slow documents.
  • Scrape vLLM’s own metrics as well, so request latency and queueing sit next to the GPU view.
  • Load-test each model on its own to find how much traffic it can take before latency climbs.
  • Add health checks that send a real test request, not just check that the container is running.
