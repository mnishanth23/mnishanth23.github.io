How the stack fits together

01

The problem

Our messaging and integration layer had grown the usual way: a broker, a Karaf container running Camel routes, and a setup script that knew how to put it all together. That works until you need to rebuild it somewhere else, or work out what changed.

  • The broker’s configuration needed to travel with the broker, with a history of changes.
  • The Karaf setup was a script you ran, rather than a stack you could declare and bring up.
  • The team needed NiFi 2 and Superset on devlab, connected to the data that already existed rather than a fresh, empty copy.
  • In production, Camel routes on Karaf 4.4.7 stopped silently while the containers still reported healthy, so nothing looked wrong from the outside.

02

What I did

  1. Containerised ActiveMQ Classic with its configuration embedded in the image and versioned, so a broker version and its config ship together.
  2. Converted the Karaf setup script to Docker Compose, turning a sequence of steps into a declared stack.
  3. Set up Apache NiFi 2 and Apache Superset on devlab, wired to the existing broker and the Postgres data-engine database.
  4. Troubleshot the production Apache Karaf 4.4.7 deployment, including the Camel routes that stopped while their containers stayed healthy.

03

How it works

Broker config that ships with the broker

Instead of mounting configuration from wherever it happens to live on a host, the broker image is built with its configuration files inside it. The config sits in version control next to the Dockerfile, so every change has a commit, and the image tag tells you exactly which config a running broker has. Rolling back the config means running the previous image.

From setup script to Compose

A setup script describes how to build an environment; a Compose file describes what the environment is. Each step in the script becomes something declared: the image, the ports, the volumes, the environment variables, the start order and a health check. Bringing the stack up, or rebuilding it, becomes one command, and a diff of the file shows what changed.

NiFi 2 and Superset on devlab

NiFi and Superset are only useful with real data behind them, so on devlab they connect to what already exists: NiFi to the existing ActiveMQ broker and the Postgres data-engine database, and Superset to that same database for dashboards and exploration. Nothing is copied into a separate sandbox that would drift.

The lesson: a healthy container is not a healthy route

The production Karaf 4.4.7 issue is the part I think about most. Camel routes stopped processing, but the containers reported healthy, because a container health check usually asks a narrow question: is the process up, is the port open? Karaf can be perfectly alive while a route inside it is stopped or stuck, and from the outside everything looks green.

My approach is to check health at the level where the work happens:

  • Route status: ask Karaf/Camel whether each route is actually started, for example via the Karaf shell’s Camel commands or Camel’s own health checks, and treat “not started” as unhealthy.
  • Broker signals: watch queue depth and consumer counts. A queue that keeps growing, or loses its consumer, is a stopped route seen from the other side.
  • Flow, not just liveness: alert when messages stop moving, not only when a container exits.
Rule of thumb

If a health check would still pass with the service doing nothing useful, it’s a liveness check. Keep it, but don’t mistake it for health.

04

Results

  • ActiveMQ Classic runs as a container with its configuration embedded and versioned.
  • The Karaf setup is a Docker Compose stack instead of a setup script.
  • NiFi 2 and Superset are running on devlab, wired to the existing broker and the Postgres data-engine database.
  • Production Karaf 4.4.7 troubleshot, including Camel routes that stopped while containers reported healthy.

05

What I’d do next

  • Make route status part of the container health check, so “healthy” means the routes are running.
  • Alert on queue depth and consumer count, alongside the uptime monitoring described in Observability and capacity.
  • Keep the Karaf and Camel configuration versioned the same way as the broker’s.
  • Write a short runbook for “container healthy, nothing moving”, so the next person starts at the right layer.
