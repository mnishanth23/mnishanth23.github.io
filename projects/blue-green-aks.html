Blue-green deployments on AKS

A personal learning project I’ve been building since September 2026: zero-downtime blue-green releases on Azure Kubernetes Service, from scratch, on a free Azure account. The target design: Terraform provisions AKS and ACR, Argo Rollouts runs the blue-green cutover, a Prometheus analysis gate decides whether a release is promoted, Azure Front Door sits in front, and GitHub Actions drives the pipeline. I’m working through it as a 13-phase plan, and it’s still in progress.

01

The problem

A plain rolling update replaces the old version gradually. For a while, both versions serve real users, and if the new one is bad, “rolling back” is just another rollout that takes time. Blue-green avoids that: the new version starts next to the old one, gets checked while users stay on the old one, and traffic moves across in a single switch. The old version stays up, so going back is one switch, too.

My day job is shipping containers through CI pipelines (see Drone CI pipeline hardening). I wanted to learn the same release discipline on a managed Kubernetes platform, end to end, and own every piece of it myself: the infrastructure code, the registry, the rollout controller, the metrics gate, the edge and the pipeline.

The constraint is part of the exercise: a free Azure account. Quota and cost are real limits, so the design has to be cheap to run and easy to tear down and rebuild.

02

What I’m doing

  1. Infrastructure as code with Terraform: the AKS cluster, the Azure Container Registry and the permission that lets the cluster pull from it, all defined in code.
  2. Blue-green with Argo Rollouts: the new version runs as a separate ReplicaSet behind a preview Service while the active Service keeps serving the current one.
  3. A Prometheus analysis gate: promotion depends on metrics from the new version, not on someone eyeballing a dashboard.
  4. Azure Front Door in front, so users always hit one stable entry point while the cutover happens behind it.
  5. A GitHub Actions pipeline that builds the image, pushes it to ACR and updates the Rollout.
  6. Working in 13 phases and writing down what I learn in the repo as I go.

03

How it works

Two versions, two Services

Argo Rollouts replaces the usual Deployment with a Rollout resource. With the blueGreen strategy, a new image creates a second ReplicaSet (green) alongside the current one (blue). The active Service keeps pointing at blue; the preview Service points at green, so the new version can be tested without any user seeing it. Promotion changes the active Service’s selector to green, so the entry point never changes. Blue is kept for a short delay before it scales down, which makes rollback a selector switch rather than a redeploy.

The gate: Prometheus decides, not a person

An Argo Rollouts AnalysisTemplate runs a Prometheus query against the green version before promotion, for example its error rate or success rate over a short window. If the result meets the condition, the Rollout is promoted; if it doesn’t, the Rollout is aborted and traffic never leaves blue. That turns “looks fine to me” into a rule that runs on every release.

The edge: Azure Front Door

Front Door is the single public entry point. The blue-green switch happens inside the cluster at the Service level, so the edge configuration doesn’t change during a release.

The pipeline: GitHub Actions → ACR → Rollout

On a push, GitHub Actions builds the image, pushes it to ACR with a version tag, and updates the image in the Rollout. That update is what starts a new blue-green release. The cluster pulls from ACR using its own identity, so no registry password is stored in the cluster.

Free account, real limits

Because it runs on a free account, the cluster only exists while I’m working on it: Terraform removes it at the end of a session and rebuilds it at the start of the next, while the registry and its images stay. Infrastructure as code isn’t a nice-to-have here; it’s what makes that routine cheap.
